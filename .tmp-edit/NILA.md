# Nila Project Guide

This is the canonical, source-aligned guide to Nila. Re-check the implementation when details here appear stale; source code is authoritative.

## Identity

- **Name:** Nila
- **Tagline:** Everything your community needs.
- **Purpose:** A public, all-in-one Discord bot. The repository currently contains the initial dashboard and shared UI foundations, not the full planned feature set.

## Technology

- Node.js, CommonJS (`package.json` sets `type` to `commonjs`)
- Discord.js `^14.27.0` (installed version inspected: `14.27.0`)
- dotenv for root `.env` loading
- Node's built-in test runner (`node:test`); there is no additional test framework
- npm workspaces: `"website"` package workspace for the Next.js web application and dashboard (`npm run dev --workspace=website`, `npm run build --workspace=website`)

No additional runtime dependency should be added without a clear need.

### Main Responsibilities

- `index.js`: side-effect-free on import (exports `startBot`, `buildClient`, `attachClientHandlers`, `handleTermination`; only starts the bot when executed directly via `node index.js`). `startBot` displays the banner, validates UI configuration, reads `DISCORD_TOKEN`, creates a Discord.js client with `Guilds`, `GuildMessages`, and privileged `MessageContent` intents, initializes runtime modules and the database, then logs in. Ready metrics are reported only on Discord.js's `clientReady` event; termination signals trigger graceful shutdown. Importing the module for tests or inspection never logs in.
- `src/startup.js`: validates embed and component configuration, loads/validates command modules into `client.commands`, registers event modules, avoids reinitializing the same client, emits initialization summaries, and formats actual ready-event data.
- `src/database/connectionManager.js`: owns one injectable official MongoClient instance, tracks connection state, shares in-flight initialization, and closes idempotently. The startup database initializer does not make MongoDB a bot-login requirement.
- `src/database/ruleRegistry.js`: describes proposed balanced defaults and strict config validators for 8 registered rules (`message_flood`, `duplicate_messages`, `mention_spam`, `blocked_keywords`, `discord_invites`, `suspicious_links`, `scam_detection`, `anti_raid`); the canonical duplicate rule id is `duplicate_messages` (plural) and the singular form is rejected as unknown. Detection is implemented for all eight rules and all eight are `available: true`; message detection covers the seven message rules while anti-raid runs on member joins. Auto-Mod defaults to disabled; `validateAutomodConfig` permits `enabled: true` only through data that passes per-rule validation (malformed enabled rules are rejected), and the only writer of enabled state is the authorized dashboard activation flow. Also exposes rule-lifecycle helpers (`getRuleDefinition`, `isRuleRegistered`, `isDetectionImplemented`, `isRuleAvailable`, `isRuleConfigured`, `describeRuleEligibility`) and the extended enforcement-action labels (`log`, `log_only`, `delete_message`, `warn`, `timeout`, `kick`, `ban`, `alert_moderators`).
- `src/database/repositories.js`: exposes fixed-name repositories for guild configs, Auto-Mod rules, incidents, warnings, allowlists, manual moderation cases, and channel lock states. Guild-scoped reads and mutations always carry a validated `guildId`. Incident records accept Phase 2 optional fields (`messageId`, `configuredAction`, `actualAction`, `outcome`, `reasonCode`, `failureReason`, `metadata`, `idempotencyKey`) while still rejecting message-content fields, and expose `findByIdempotencyKey` for duplicate-delivery handling. Moderation cases live in `moderation_cases` with atomic per-guild sequential `caseId` values from `moderation_case_counters` (see the Manual Moderation section below).
- `src/automod/`: Phase 2 rule framework and enforcement engine (no listeners, no intents, no slash commands). `detectionResult.js` validates untrusted detector claims; `actionRegistry.js` defines the 7 supported actions plus the `log` legacy alias and severe-action severity gates; `exemptions.js` merges guild config and allowlist exemptions; `warnings.js` records/counts guild-scoped warnings with best-effort dedupe and advisory escalation; `incidents.js` records incidents with idempotency handling and explicit persistence reporting; `discordActions.js` executes Discord calls behind permission, hierarchy, ownership, and privileged-member guards; `policyEngine.js` (`processDetection`) runs the 12-step fail-closed enforcement flow; `detectors/` holds the Phase 3A message detectors (see below); `index.js` offers idempotent `initializeAutomod`/`shutdownAutomod` with no side effects.
- `src/database/config.js`: validates MongoDB environment configuration without including connection values in diagnostics.
- `src/moderation/`: manual moderation services. `moderationService.js` owns reusable Phase M1 `warn`, `timeout`, `untimeout`, `kick`, `ban`, `unban`, and warning-history operations over plain guild/member objects (no Discord interaction import, so a future authenticated web dashboard can reuse it); `guards.js` holds the shared Phase M2 permission/identity/persistence helpers (M1 is intentionally untouched); `purgeService.js`, `channelService.js` (slowmode/lock/unlock), and `historyService.js` (modlogs queries) implement the Phase M2 operations the same interaction-free way; `interactions.js` wires all service results to Nila embeds and ephemeral responses. No listeners, no intents, no dashboard.
- `src/tickets/`: ticket-system foundation (T1) plus member-facing panels (T2). Interaction-free and listener-free: every operation is a plain async call on a service, so commands, component handlers, and a future authenticated web dashboard all reach the same logic. `index.js` (`createTicketSystem` / `getTicketSystem`) wires one service graph over the shared repository set and logger; it creates no Discord listeners and never logs in. `constants.js` holds the vocabularies (statuses, sync states, health states, priorities, closed-access modes, event types, limits, `formatTicketKey`), `errors.js` holds the `failure()`/`success()` result contracts plus the Discord-error mapper, and `validation.js` holds the shared field validators every write passes through. T2 adds `panels/` (layout limits, custom IDs, renderer, opening forms, welcome messages, ticket controls, interaction handler), `validators/panelValidator.js`, and `services/panelService.js`.
- `src/tickets/validators/`: `configValidator.js` (full-document guild-config validation and `mergeTicketConfigPatch`, which rejects `enabled` outright), `categoryValidator.js` (`createDefaultTicketCategory`, `mergeCategoryPatch` with immutable identity/audit fields), `ticketValidator.js` (`validateTicketRecord`, `validateTicketEvent`, `buildChannelName`, opening-answer validation, channel-name building), `transcriptValidator.js` (guild transcript policy and transcript metadata), `noteValidator.js` (staff-note records with bounded edit history).
- `src/tickets/services/permissionService.js`: the single authorization point for all ticket actions (now including staff-note actions), evaluated at the moment each operation runs.
- `src/tickets/services/configService.js` and `categoryService.js`: guild settings and ticket-category management, including the separate authorized enable/disable path and the member-facing category projection.
- `src/tickets/services/ticketService.js`: ticket creation (including the T2 opt-in `skipWelcomeMessage` flag) and every lifecycle operation (claim, release, assign, participants, rename, priority, transfer, close, reopen, listing, history) with structured failures and audit events. `closeTicketByAutomation`/`reopenTicketByAutomation` (Phase T5.5.3) reuse the exact manual close/reopen internals with state guards instead of member authorization; there is no second lifecycle implementation.
- `src/tickets/services/panelService.js`: Phase T2 panel management, validation, ordered-category resolution, ephemeral preview, publish, published-message update, and republish over the `ticketPanels` repository, all behind `MANAGE_CATEGORIES` authorization.
- `src/tickets/services/channelService.js`: the only ticket module that touches Discord channels — pre-flight permission checks, the deterministic overwrite policy, and create/rename/move/send/delete adapters with ownership verification and Discord-error mapping.
- `src/tickets/services/recoveryService.js`: post-startup reconciliation of interrupted operations from their persisted markers; cache-only, bounded, never fatal, and never destructive.
- `src/database/ticketRepositories.js`: the ticket collections, their 18 index definitions, atomic per-guild ticket-number allocation, the revision-guarded conditional-write primitives, and the unreconciled-record query recovery uses. It is mounted inside the existing repository layer, so the collection allowlist and the one connection manager are shared.
- `src/commands/nila.js`: defines `/nila` and renders Overview, Features, Server Setup, and Help dashboard pages. Navigation updates the existing ephemeral message and is restricted to the initiating user. Status data is sourced from the live client and current guild where available. `setDMPermission(false)` restricts the command to guild contexts only.
- `src/commands/ticket-panel.js`: defines `/ticket-panel` (Phase T2) with `create`, `list`, `preview`, `publish`, `update`, `disable`, and `delete` subcommands over the panel service; destructive deletes use the shared confirmation flow and every call rechecks Manage Server rights.
- `src/commands/tickethelp.js`: defines `/tickethelp` (master milestone usability) with an optional `topic` choice (overview, open, my-tickets, staff, admin) over the panel and ticket services; ephemeral role-appropriate guidance plus live caller-allowed data only (published panel locations, the caller's own tickets). `setDMPermission(false)` restricts it to guild contexts because all ticket data is guild-scoped. Loads through the existing startup scan; intentionally absent from `scripts/deploy-commands.js` (still 18) until a future explicit deployment includes it.
- `src/commands/tickets.js`: defines the guild-only `/tickets` configuration dashboard (Phase T3, the single setup-and-management entry point) with thirteen Components V2 views — Overview, Setup guide (saved progress plus next-step jumps, computed through the shared setup service), Panels, Categories, Opening forms, Appearance, Permissions & routing, Automation (live values plus tuning editors and explicitly confirmed activation through the shared setup operations), Logs & transcripts, Limits, Staff insights (read-only workload/volume with pointers to `/ticket`), Help (plain-English setup order and staff commands), Review & activation — guild-scoped sliding-TTL sessions, per-interaction authorization, modal editors, and two-step confirmations; business rules live in `src/tickets/dashboard/service.js`, Discord wiring in `src/tickets/dashboard/ops.js` + `modals.js`. Expired sessions render a Reopen button that the stale-interaction path turns into a brand-new manager-verified session. `setDefaultMemberPermissions(ManageGuild)` and `setDMPermission(false)` are both declared so Discord enforces visibility restrictions at the protocol layer, complementing the server-side `isTicketManager()` check inside `execute()`.
- `src/commands/ticket-setup.js`: defines the guild-only `/ticket-setup` end-to-end configuration wizard: eight paginated Components V2 pages (Overview, Categories, Permissions, Forms & messages, Panel designer, Publishing, Automation & advanced, Final review) that edit the live saved configuration through the existing validated services (`src/tickets/setup/service.js` thin wrappers over config/category/panel/reminder/lifecycle/survey/automation-policy services, modal builders in `src/tickets/setup/modals.js`). There is no draft: changes persist immediately with server-side validation and revision-guarded concurrency (stale writes reload instead of overwriting); destructive, publishing, and enabling actions always require explicit confirmation, and publishing/enabling never happen merely by reaching a page. Sessions are guild-scoped, owner-restricted, sliding-TTL with per-interaction manager rechecks. `/ticket` also routes a future `setup` subcommand to the same wizard, but declares none today because `/ticket` already fills Discord's 25-option limit. `setDefaultMemberPermissions(ManageGuild)` and `setDMPermission(false)` are both declared so Discord enforces visibility at the protocol layer, complementing the server-side `isTicketManager()` check inside `execute()`. Loads through the existing startup scan; intentionally absent from `scripts/deploy-commands.js` (still 18) until a future explicit deployment includes it.
- `src/commands/warn.js`, `warnings.js`, `timeout.js`, `untimeout.js`, `kick.js`, `ban.js`, `unban.js`: thin Phase M1 handlers. Each reads interaction options, calls the moderation service, and renders the real outcome; permission, hierarchy, and persistence logic lives in the service, not the handlers.
- `src/commands/purge.js`, `slowmode.js`, `lock.js`, `unlock.js`, `modlogs.js`: thin Phase M2 handlers over the purge/channel/history services, following the same pattern.
- `src/commands/automod.js`: defines `/automod`, an administrator-only ephemeral Components V2 dashboard (Overview, Rule Settings, Enforcement, Exemptions, Logging, Review & Activation) built on one shared configuration draft per editing session with global Undo Changes / Save Changes controls. Pure draft logic lives in `src/automod/dashboardConfig.js`; `src/automod/activation.js` owns the explicit enable/disable services with stale-configuration and persistence checks. Opening, editing, previewing/applying the preset, saving, or navigating never enables protection; activation is a separate confirmed operation and requires the draft to be saved or discarded first. `setDefaultMemberPermissions(Administrator)` and `setDMPermission(false)` are both declared so Discord enforces the administrator-only restriction at the protocol layer, in addition to the server-side `isAdministrator()` check inside `execute()` and every session interaction handler. See the Phase 3B section below.
- `src/events/interactionCreate.js`: dispatches chat-input commands from `client.commands`, identifies stale dashboard controls, routes `/tickets` dashboard and `/ticket-setup` wizard IDs plus ticket-panel custom IDs to their handlers, and reports unexpected interaction failures.
- `src/events/messageCreate.js`: feeds guild messages through detection into the Phase 2 policy engine. Skips bots, webhooks, system messages, partials, DMs, and malformed events; reads (never creates) guild configuration and returns early while Auto-Mod is disabled; resolves own-invite codes best-effort with a bounded TTL cache; never punishes directly. Registered once per client via the startup event scan.
- `scripts/deploy-commands.js`: explicitly registers the 18-command set (`/nila`, `/automod`, `/warn`, `/warnings`, `/timeout`, `/untimeout`, `/kick`, `/ban`, `/unban`, `/purge`, `/slowmode`, `/lock`, `/unlock`, `/modlogs`, `/ticket-panel`, `/tickets`, `/transcript`, `/ticket`); deployment is not run automatically by bot startup.
- `src/config/embeds.json`: traditional embed brand, palette, templates, messages, and display/interaction defaults.
- `src/config/components.json`: Components V2 layout, text, button, select, pagination, expiry, and presentation conventions. Colors and brand are referenced from the embed config.
- `package.json` / `package-lock.json`: include the official `mongodb` Node.js driver in addition to discord.js and dotenv.
- `src/utils/README.md`: examples and contracts for the shared UI utilities.
- `test/`: offline regression tests for commands, startup, logging, embed behavior, and Components V2 behavior.

## Startup and Commands

The runtime command module contract is `{ data, execute }`, where `data` is a Discord.js `SlashCommandBuilder`. `src/startup.js` scans flat JavaScript files in `src/commands`, validates each export and Discord name/description constraints, and only then inserts it into `client.commands` and reports it as loaded. The current commands are `/nila`, `/automod`, `/warn`, `/warnings`, `/timeout`, `/untimeout`, `/kick`, `/ban`, `/unban`, `/purge`, `/slowmode`, `/lock`, `/unlock`, `/modlogs`, `/ticket-panel`, `/tickets`, `/transcript`, `/ticket`, `/tickethelp`, and `/ticket-setup` (20 loaded; deployment still registers the explicit 18-command list until future deployments include the help and setup commands).

Event modules export `{ name, register(client, logger) }`. Startup reports an event after successful registration. The `interactionCreate` listener is registered once per client and dispatches using that client's loaded command collection. The `messageCreate` listener is registered once per client the same way and routes messages through detection into the policy engine.

Command publication is separate from runtime startup:

- `npm run deploy:commands` defaults to guild registration using `DISCORD_CLIENT_ID` and `DISCORD_GUILD_ID`.
- `COMMANDS_SCOPE=global` explicitly selects global registration; propagation can take time.
- Deployment uses a Discord REST bulk overwrite for the selected scope. The current deployment list contains all eighteen commands above; understand this overwrite behavior before adding commands or changing deployment code. Run `npm run deploy:commands` explicitly after pulling this phase; without it, the new moderation commands will not appear in Discord.
- `scripts/deploy-ticket-setup.js` (`npm run deploy:ticket-setup -- <TEST_GUILD_ID>`) registers only `/ticket-setup` in one explicitly passed private test guild via a single-command POST (other guild commands preserved, global scope impossible, `DISCORD_GUILD_ID` never consulted). Nothing is deployed automatically; run it explicitly for private testing only.

## MongoDB Foundation

Install/configure MongoDB privately by setting `MONGODB_URI` and `MONGODB_DATABASE` in the root `.env` or deployment environment. Do not put credentials in documentation, source, logs, or chat. Startup explicitly attempts database initialization with a bounded server selection timeout. MongoDB unavailability does not prevent the Discord bot from starting, but repositories are not an in-memory fallback: accessing them while disconnected raises a database-unavailable error.

For MongoDB Atlas, create a least-privilege database user, restrict the project's network access list to the bot host, and copy the driver connection URI into the private environment. For self-hosted MongoDB, use authentication and TLS, bind the service to a private interface, restrict firewall access to the bot host/VPN, and keep credentials in a protected secret store. Never expose MongoDB directly to the public internet without network and transport protections.

The official `mongodb` Node.js driver is used directly; no ODM is present. `src/database/index.js` initializes the connection and creates stable indexes (57 in total: 17 for Auto-Mod/moderation — including the partial-unique `guildId + idempotencyKey` duplicate-delivery guard and the `guildId + ruleId + userId + outcome + createdAt` per-rule cooldown read — 18 for the T1 ticket collections including the two panel indexes, 4 for the T5.1 transcript metadata collection, 2 for the T5.2 staff-note collection, 1 for the T5.3 event time-series shape, 7 for the T5.4 survey collections, and 8 for the T5.5 automation collections, which cover both the foundation jobs/events/policies shapes and the reminder activity/invalidation shapes). `repositories` exposes `guildConfigs`, `automodRules`, `automodIncidents`, `automodWarnings`, `automodAllowlists`, `moderationCases` (manual moderation audit records with guild-scoped sequential case IDs), `moderationChannelStates` (persistent @everyone SendMessages states saved by `/lock` for `/unlock` restoration), the ticket repositories `ticketConfigs`, `ticketCategories`, `tickets`, `ticketEvents`, `ticketCounters`, `ticketPanels`, `ticketTranscripts`, `ticketNotes`, `ticketSurveys`, and `surveyResponses`, and the automation repositories `ticketAutomationJobs`, `ticketAutomationEvents`, `ticketAutomationPolicies`, and `ticketActivity`, plus the platform-wide `changelog` (a single global document with a unique `key` index and revision CAS); it does not expose arbitrary collection access. Incident input rejects message-content fields. Dates are stored as JavaScript `Date` values for BSON date storage. No code in the project uses MongoDB transactions: ticket integrity comes from unique indexes and conditional writes instead.

`src/database/ruleRegistry.js` defines proposed balanced starting values for flooding, duplicates, mention spam, blocked keywords, invite filtering, suspicious links, scam sensitivity, and anti-raid join limits. These values are not universal policy recommendations. Per-guild thresholds, actions, exemptions, logging channel, and warning escalation are represented in the data model. Detection is implemented for all eight rules and all eight are available for activation. All defaults are disabled. Configuration flows through two surfaces that share one stored model: the `/automod` Discord command and the website Auto-Mod console (see "Auto-Mod Website Console"). Both write the same `guild_configs.automod` document, and every production enforcement passes the policy engine's fail-closed checks regardless of which surface saved the rule.

Stored per-rule settings are the registry's own rule config (enabled, sensitivity, thresholds, action, rule lists) plus the per-rule override keys now used by both surfaces: `severity` (review label only — it never unlocks `kick`/`ban`, which are gated by the detector's own severity), `cooldownSeconds` (0–86400, suppresses repeat member/message actions read from durable incident history rather than memory), `timeoutSeconds` (1–2419200, replaces the engine default), `escalationEnabled` (must be true alongside the guild warning policy for escalation to run), and `exemptRoleIds`/`exemptChannelIds`/`exemptUserIds` (≤100 snowflakes each, checked after the guild-wide exemptions). Only `undefined` means "no override": an explicit `null` is a validation error, so clients clear an override by omitting the key. Old documents without these keys stay valid and are never rewritten.

## Auto-Mod Enforcement Engine (Phase 2)

Implemented in `src/automod/` (dependency-injected, offline-testable, no Discord listeners):

- **Rule lifecycle:** registered vs. detection-implemented vs. configured vs. enabled vs. eligible-to-execute are distinct. `describeRuleEligibility` reports the exact blocking stage. All eight rules are `available: true` with implemented detectors; only enabled, validly configured rules execute.
- **Detection contract:** `validateDetectionResult` normalizes `guildId`, `ruleId`, `channelId?`, `messageId?`, `userId`, `detectedAt`, `confidence?` (0–1), `severity?` (`low`/`medium`/`high`/`critical`), `reasonCode`, flat minimal `metadata?` (≤20 entries, no content/secret keys), and `eventId?` for idempotency. Unknown rules, bad snowflakes, malformed timestamps, and content-bearing metadata are rejected before enforcement.
- **Enforcement flow (`processDetection`):** validate → duplicate-event guard → load guild config (fail closed on DB errors/missing config) → require explicit Auto-Mod enablement → paused check (`AUTOMOD_PAUSED`: no Discord action and no incident record) → rule registered/configured/enabled/available/implemented → Discord-object consistency check → guild exemptions, then the separate verified allowlist, then per-rule exemptions → resolve and validate action → severity gate for `kick`/`ban` → detection-only simulation short-circuit → permission/hierarchy execution → warning persistence (for `warn`) → escalation execution → incident recording. Returns `{ outcome: executed|skipped|failed|simulated, actionTaken, reasonCode, incidentRecorded, ... }`.
- **Action support:** `log_only`, `delete_message`, `warn`, `timeout` (1–2419200s, default 600s), `kick` (requires `high`/`critical` severity), `ban` (requires `critical` severity), and `alert_moderators` (requires a log channel) are all implemented behind guards; `log` persists as a legacy alias of `log_only`. Unknown actions are rejected. `warn` delivers one visible reply to the offending message (no content echoed) in addition to the persisted warning/incident records; undeliverable warnings degrade to persistence-only with a `WARN_DELIVERY_UNAVAILABLE`/`DISCORD_API_ERROR` code instead of failing.
- **Discord safety:** bot permission, role-hierarchy, guild-owner, Administrator, and bot-self protections; missing members/messages/channels produce structured codes (`PERMISSION_DENIED`, `HIERARCHY_BLOCKED`, `OWNER_PROTECTED`, `PRIVILEGED_MEMBER`, `TARGET_UNAVAILABLE`, `MESSAGE_NOT_FOUND`, `ALREADY_TIMED_OUT`, `DISCORD_API_ERROR`, `INVALID_TIMEOUT`). Raw Discord errors never reach callers. No mass/bulk actions exist.
- **Exemptions:** precedence is fixed and tested — guild `exemptRoleIds`/`exemptChannelIds` are checked first, then the stored allowlists (`user`/`role`/`channel`), then the rule's own `exempt*Ids`. Exempt events skip punishment but still record a `log_only` audit incident (`EXEMPT_USER`/`EXEMPT_ROLE`/`EXEMPT_CHANNEL`, or `RULE_EXEMPT_*` for the per-rule lists, which label the record as rule-scoped). There is no guild-wide `exemptUserIds` key in the schema: member exemptions are either per-rule or allowlist entries.
- **Runtime modes:** `automod.mode` (`enforce` | `detection_only`) and `automod.paused`/`pauseReason` live in the same guild document. Detection-only runs every check above, then records the incident as `outcome: "simulated"`, `reasonCode: "DETECTION_ONLY"`, `actualAction: "none"` and performs no Discord call, no warning delivery, and no escalation. A pause short-circuits before rule decisions and records nothing.
- **Cooldowns:** per-rule `cooldownSeconds` is read from durable incident history (newest executed incident for guild+rule+member inside the window), so a worker restart cannot reset a suppression window; visibility actions (`log_only`, `alert_moderators`) are never suppressed, a suppressed enforcement records a `skipped`/`COOLDOWN_ACTIVE` incident with the computed `cooldownUntil`, and a cooldown read that cannot be answered fails closed instead of assuming "no cooldown".
- **Warnings/incidents:** guild-scoped warning records with a 60s dedupe window, windowed counts, and executed escalation (the configured `timeout` once the rule's threshold is reached, never kick/ban and never while detecting only); incidents carry configured vs. actual action, outcome, severity, reason/failure codes, and the `guildId + idempotencyKey` partial-unique index that makes duplicate delivery a real dedupe rather than a best-effort check. An executed action with a failed incident write returns `incidentRecorded: false` with `INCIDENT_PERSISTENCE_FAILED` rather than claiming persistence.
- **Fail-closed codes:** `INVALID_DETECTION`, `UNKNOWN_RULE`, `CONTEXT_MISMATCH`, `DATABASE_UNAVAILABLE`, `MISSING_CONFIG`, `AUTOMOD_DISABLED`, `RULE_NOT_CONFIGURED`, `RULE_DISABLED`, `RULE_UNAVAILABLE`, `DETECTOR_UNIMPLEMENTED`, `UNKNOWN_ACTION`, `SEVERITY_INSUFFICIENT`, `DUPLICATE_EVENT`, plus the Discord safety codes above. User-facing surfaces must map these to safe messages without raw errors or secrets.

## Message Detection (Phase 3A)

Implemented in `src/automod/detectors/` plus `src/events/messageCreate.js`. Detectors are pure functions over a message snapshot; they never call Discord APIs, never punish, and every finding is re-validated against the detection-result contract before reaching `processDetection`.

- **Implemented detectors:** `message_flood` (rolling-window frequency; triggers above `maxMessages`, default 6 per 10s), `duplicate_messages` (NFKC/case/whitespace-normalized SHA-256 comparison; triggers at `repeatCount`, default 3 per 30s), `mention_spam` (distinct users + roles + `@everyone` as 1; triggers above `maxMentions`, default 5), `blocked_keywords` (literal `contains`/`exact` matching, no regex; empty list never flags), `discord_invites` (strict `discord.gg` / `discord.com/invite` / `discordapp.com/invite` parsing with `allowedCodes` and best-effort `allowOwnGuild` exemptions), `suspicious_links` (deterministic hostname checks — blocklist, brand-subdomain, lookalike, IP literal, credentials, percent-encoding, unusual port, shortener policy — plus optional caller-resolved reputation verdicts and per-guild blocked/trusted domain lists), `scam_detection` (multi-family heuristics — Nitro/giveaway, credential theft, impersonation, urgency, secrecy, external contact — plus strong-URL signals; severity capped at high so it can never satisfy the ban gate alone).
- **Anti-raid:** join-rate monitoring on `guildMemberAdd` via `src/automod/raid.js` (bounded rolling window per guild, cooldown, maximum-active ceiling, account-age gate, DB-persisted raid state with memory-only fallback); each join while raid mode is active yields at most one per-member finding for the policy engine — no mass actions. Requires the privileged `GuildMembers` intent.
- **Required gateway intents:** `Guilds`, `GuildMessages`, privileged `MessageContent`, and privileged `GuildMembers`. Enable **Message Content Intent** and **Server Members Intent** in the Discord Developer Portal (application → Bot → Privileged Gateway Intents); without Message Content, message text arrives empty and content-based detectors degrade to no-ops while flood (frequency-only) and mention (parsed collections) detection still work; without GuildMembers, `guildMemberAdd` never arrives and anti-raid stays offline with a logged hint.
- **Configuration defaults:** all Phase 1/2 balanced defaults are unchanged and everything stays disabled. Receiving a message, joining a guild, or starting the bot never enables Auto-Mod and never creates configuration documents (the handler reads with `get`, never `ensure`).
- **Pipeline diagnostics:** `messageCreate` emits `debug`-level structured lines (off by default) for evaluation (guild/message ids, enabled-rule and keyword counts), matches (rule:reason pairs), and enforcement outcomes (outcome, reason code, executed flag). Disabled-protection skips are logged the same way. Message content, tokens, and secrets are never logged; objects pass through the logger's credential sanitizer.
- **State retention and memory limits:** the tracker store keeps per-guild/per-user timestamps and content hashes only (never message text), with caps of 500 guilds, 1000 users per guild, 120 timestamps and 40 hashes per user, and 5000 processed message ids; oldest entries evict first, windows prune lazily, and no timers are created. Own-invite codes cache at most 200 guilds for 10 minutes.
- **Known detection limitations:** no semantic or image/attachment analysis; `blocked_keywords` matches literal strings only (`contains`/`exact`, never regex; `exact` requires the whole message to match), so it is not an obfuscation defence against leetspeak, homoglyphs, spacing or zero-width tricks; `suspicious_links` is deterministic hostname heuristics and there is no reputation or threat-intelligence feed, so no verdict of "malicious" is claimed and the bot process never fetches a user-supplied URL; `scam_detection` heuristics produce false positives and cap at `high` severity; invite detection flags textual invite references (including quoted ones) and cannot verify `allowOwnGuild` when the guild's invite list is unfetchable (flags for review instead); flood/duplicate windows are per-process memory and reset on restart; join windows are per-process memory while raid active state persists in MongoDB; raid signals alone never justify a kick or ban — the engine will not accept them as a severe-action trigger. Anti-raid testing starts in detection-only mode.

- **Modal lifecycle (Keywords / Invite codes / Link domains):** modal opener buttons live on a separate persistent collector so `showModal` is never preceded by `deferUpdate`. Text-input labels stay within Discord's 45-character limit (longer hints go in placeholders). The modal submit custom IDs are registered as active dashboard IDs while the session lives, so the `interactionCreate` router passes a valid modal submit through unacknowledged and `awaitModalSubmit` answers it exactly once with `submit.update(...)` — this replaces the old router/collector double-acknowledgement that surfaced Discord error 10062. Submits are acknowledged before any work (edits touch only the shared draft, never MongoDB); if a token is already spent or expired, the reply is skipped after one sanitized log instead of retrying the acknowledgement. Expired sessions apply nothing and persist nothing; re-running `/automod` creates a fresh session.

- **Shared draft (Save/Undo Changes):** every section edits one draft; the session keeps the original persisted snapshot (`savedSnapshot`) separate from the working `draft`, and dirty state is canonical-JSON comparison plus pending user-exemption adds/removes — nothing writes to MongoDB until Save Changes. A global `↩ Undo Changes` / `✓ Save Changes` row renders in every section (Overview, Rule Settings, Enforcement, Exemptions, Logging, Review) and every view stays inside Discord's documented 40-component budget for one Components V2 message. Each section displays draft values, navigation preserves unsaved changes, and the dashboard always shows the draft status line. Every view stays inside Discord's documented 40-component budget for one Components V2 message. All values validate server-side with registry bounds before touching the draft.

Removals stage into the shared draft only — Save Changes persists them, Undo Changes discards them — so a removal is a two-step confirmed operation and stale selections are rejected without touching other entries. The Exemptions view lists effective users/roles/channels (saved plus staged adds minus staged removals) with per-kind empty messages; user adds/removes apply as per-entry allowlist operations on save.

- **Exemptions/logging:** role/channel picks are verified against the guild before entering the draft (unknown IDs are dropped with a notice); user picks are format-validated (Discord menus already scope them; only admins reach this code and the effect is benign). Removal, log-channel pick/clear, and missing-entity handling are covered. All reads/writes stay guild-scoped.

Confirm rechecks admin rights, rejects drafts changed since review or with unsaved changes, rejects stale database state via `updatedAt` comparison, validates, writes once with `enabled: true`, then re-reads to confirm; success syncs the saved snapshot to the now-active draft. Any failure (including MongoDB outage) leaves the guild disabled. Duplicate confirms process a single enablement. Deactivation follows the same guarded path, keeps stored settings, and refreshes the snapshot from the re-read document.

## Manual Moderation (Phase M1)

Implemented in `src/moderation/` plus seven thin command handlers in `src/commands/`. No web dashboard exists; the service takes plain guild/member objects (never an interaction), so a future authenticated dashboard can reuse the same operations.

- **Commands:** `/warn member reason?`, `/warnings member`, `/timeout member duration reason?`, `/untimeout member reason?`, `/kick member reason?`, `/ban member reason? delete_message_seconds?`, `/unban user_id reason?`. All are guild-only (`DMs` rejected) with action-specific default member permissions (`ModerateMembers` for warn/warnings/timeout/untimeout, `KickMembers` for kick, `BanMembers` for ban/unban); registration defaults are defense-in-depth only — every action rechecks permissions server-side. Timeout `duration` accepts seconds or `30s`/`10m`/`2h`/`7d`/`4w` (1s–28d, Discord's maximum). Ban `delete_message_seconds` is bounded to 0–604800 (7 days). Unban `user_id` must be a 17–20 digit snowflake. Reasons are optional and default to the neutral string `No reason provided.` (records that none was given; never invents misconduct details); explicit reasons are trimmed to 512 characters.
- **Authorization:** moderator permission, bot permission (except warn, which performs no Discord call), target resolution, guild-owner immunity, bot-self and self-action refusal, moderator-vs-target and bot-vs-target role hierarchy (guild owners bypass hierarchy), and a privileged-member guard for timeout (non-admin moderators cannot timeout administrators, matching Discord's API). Untimeout refuses members who are not timed out; kick/ban fail safely when the target is unresolvable; unban validates the ID and reports `NOT_BANNED` (Discord 10026) without claiming changes. Discord rejections (including native 50013 permission failures) surface as `DISCORD_API_ERROR` with no case recorded — success is never claimed when Discord rejects the action.
- **Cases:** one document per completed action in `moderation_cases` (`guildId`, sequential guild-scoped `caseId` from the atomic `moderation_case_counters` collection, `targetUserId`, `moderatorUserId`, `action`, `reason`, `createdAt`/`outcome` as BSON dates/enums, plus `durationSeconds`/`expiresAt` for timeouts and `metadata.deleteMessageSeconds` for bans). No tokens, credentials, or message content are stored. Indexes enforce one unique `(guildId, caseId)` pair plus guild/target/chronological lookups. An optional `idempotencyKey` (command handlers pass `interaction.id`) returns the already-recorded case with `deduplicated: true` instead of re-executing Discord. A Discord success followed by a database failure returns `ok: true` with `auditPersisted: false` and `AUDIT_PERSISTENCE_FAILED` — never a saved-case claim. Warn persistence failures mean the warn did not happen (`CASE_PERSISTENCE_FAILED`, no case ID).
- **Warnings:** manual warnings live only in `moderation_cases` (`action: "warn"`); Auto-Mod warnings remain in `automod_warnings` with rule-scoped semantics and are never mixed. `/warnings` requires moderation permission, queries only the current guild/target, returns the 10 most recent (bounded to 1–25) with a total count and truncation note, and resolves departed members by user ID. Affected users are not DM'd by the warn command itself; the optional member-notification DM is a separate, disabled-by-default guild setting added in Phase M3.
- **Responses:** all replies are ephemeral embeds via the shared builders: success (completed + case number), warning (denied/invalid/not-found, or completed-but-audit-unsaved), error (Discord/DB failures). Raw errors, stacks, and internals never reach users; sanitized diagnostics go to the logger.

## Manual Moderation (Phase M2)

Implemented in `src/moderation/` (`guards.js`, `purgeService.js`, `channelService.js`, `historyService.js`) plus five thin command handlers in `src/commands/`. Phase M1 files are untouched. No web dashboard exists; all services take plain guild/channel/member objects (never an interaction).

- **Commands:** `/purge amount user? reason?` (1–100, `ManageMessages`), `/slowmode seconds channel? reason?` (0–21600s, 0 disables, `ManageChannels`), `/lock channel? reason?` (`ManageChannels`), `/unlock channel? reason?` (`ManageChannels`), `/modlogs member? user_id? action? page?` (`ModerateMembers`, 5 cases per page, up to 20 pages over the 100 most recent). All are guild-only with the listed default member permissions as defense-in-depth; every action rechecks moderator and bot permissions server-side at execution time. Reasons default to `No reason provided.` and cap at 512 characters.
- **Purge:** one Discord bulk operation at most. The unfiltered path calls `bulkDelete(amount, filterOld=true)`; the user-filtered path performs exactly one bounded fetch (≤100 recent messages), keeps only fresh (<14 days) messages from that user up to the requested amount, and still passes `filterOld=true`, so messages 14 days or older are never sent to the bulk-delete API. Only the resolved collection size is reported as deleted; API failures (including rate-limit rejections) resolve to `DISCORD_API_ERROR` with no case recorded. Metadata stores channel, requested/deleted counts, optional user filter, and the measured old-message skip count — never message content, which is also never logged.
- **Slowmode:** validated type allowlist plus a `setRateLimitPerUser` capability check; Discord failures report honestly with no case.

If the Discord edit fails, the saved row is rolled back so storage never claims an unapplied lock. Repeated locks keep the original saved state and report `alreadyLocked`. `/unlock` restores exactly the saved state (`neutral` clears the bit) and clears the row only after success; a missing row fails safely with `NO_SAVED_STATE` and a manual-restoration note instead of guessing. Both record audit cases with previous/restored-state metadata; Discord-success-plus-DB-failure keeps the M1 `AUDIT_PERSISTENCE_FAILED` distinction.
- **Modlogs:** guild-scoped `moderation_cases` reads only (plus a same-filter `count` for page boundaries), optional action/target filters, departed members resolvable by ID, channel-scoped actions rendered as channel mentions, reasons truncated, no message content or unnecessary private details. Out-of-range pages fail with `PAGE_OUT_OF_RANGE` rather than showing another guild's or wrong page's data; DB outages report `DATABASE_UNAVAILABLE`.

## Moderation DM Notifications (Phase M3)

Implemented in `src/moderation/moderationService.js` (a best-effort member DM fired inside the shared service), the new `guild_moderation` collection + `moderation` repository in `src/database/repositories.js` (one unique index `guild_moderation_guild_unique`; the guarded totals in `test/database.test.js` are now 29 collections and 67 indexes), two bridge operations in `src/dashboard/operations.js` (`moderation.notify.get` read, `moderation.notify.set` revision-guarded), and the "Member notifications" toggle in the dashboard `Moderation` surface (`website/src/components/dashboard/ConnectedDashboard.tsx` over the pure `website/src/lib/moderation-notify.ts`). Because the DM lives in the service — not the command or the bridge op — the Discord `/warn|/timeout|/ban` commands and the web dashboard behave identically; enabling the toggle is the only way any DM is ever sent.

- **What it does:** when the guild toggle is on, a successful `warn`, `timeout`, or `ban` sends the affected member one plain-text DM (a fixed branded template — action, the recorded reason, a human duration for timeouts, and the server name). The moderator's identity is deliberately never included. Untimeout, unban, and kick never DM (`DM_NOTIFY_ACTIONS` is exactly `warn`/`timeout`/`ban`).
- **Disabled by default / fail-closed:** a guild with no `guild_moderation` document reads as `dmEnabled: false`; when storage is unreachable the service's notify read throws into a `skipped_storage` result and sends nothing. The toggle can never DM by accident.
- **Best-effort, never a side effect on the outcome:** delivery is wrapped so a closed/blocked DM (`failed`), a missing user (`skipped_no_user`), a disabled toggle (`skipped_disabled`), or an unreadable config (`skipped_storage`) each still returns the real moderation result unchanged with a `dm` marker; the moderation action and its audit case never depend on the DM. A duplicated request returns before the DM step, so it never sends twice; for `ban`, the DM is attempted once the Discord removal has actually happened, even if the audit write later fails.
- **Server-side authorization:** the notify ops require `ModerateMembers` on top of the executor's global `ManageGuild` gate; a stale `expectedRevision` yields `MODERATION_STALE` (409) and writes nothing, and a non-boolean `dmEnabled` is rejected as `INVALID_BODY` before any write.
- **UI honesty:** the dashboard control is hidden until `moderation.notify.get` answers (never shown as an operational ON/OFF), and a rejected save keeps the last known state exactly.

## Counting Game (Phase C1)

A community counting-game channel: members post numbers in sequence (start, start+1, …) in one guild-designated channel and Nila validates every post. Implemented in `src/counting/` (`validation.js`, `service.js`, `index.js`), the `guild_counting` (config, revision CAS) and `guild_counting_state` (run state, high-write) collections + `counting`/`countingState` repositories in `src/database/repositories.js` (two unique indexes `guild_counting_guild_unique` and `guild_counting_state_guild_unique`; guarded totals are now 31 collections and 69 indexes), a counting step added inside the single existing `src/events/messageCreate.js` listener (no new listener), the guild-only `/counting` command, three bridge operations (`counting.get`, `counting.save`, `counting.activate`), and a `counting` dashboard section (`website/src/lib/counting-view.ts` + the `Counting` connected editor + the control-free `CountingContent` fallback under a new Community nav group).

- **Rules:** the next post must equal the stored run's value + 1 (or the configured `startNumber` for a fresh run). A wrong number posts a correction and **resets the run to the start** (the record `best` survives). The same member may **not** count twice in a row and a number posted inside the per-count `cooldownMs` is rejected — neither resets. Non-numeric chatter and messages in any other channel are ignored. Bots, webhooks, system messages, and DMs never reach the step (the shared message snapshot drops them). Correct counts advance through a compare-and-set on the run's current value, so two near-simultaneous posts produce exactly one increment (the loser is a silent miss). A counting correction never resolves mentions (no ping) and a failed send never changes the run state.

## Ticket System Foundation (Phase T1)

Implemented in `src/tickets/` plus `src/database/ticketRepositories.js`. This is the storage, service, permission, and recovery foundation only: there is **no ticket command, no ticket dashboard, and no transcript export yet**, so nothing in a server can open a ticket through Discord until those interfaces are built and authorized. `src/tickets/index.js` exports `createTicketSystem(options)` (dependency-injected repositories, logger) and `getTicketSystem()` (the single lazily-created instance handlers use). The module registers no listeners, requests no intents, and never logs in.

### Architecture and boundaries

- **Handlers never hold logic.** Every ticket operation is an async service call that takes plain Discord objects (`guild`, `member`) and identifiers, and returns a structured result. Commands, component handlers, and a future authenticated web dashboard call the same six services; no interface has a private path to storage.
- **`channelService` is the only Discord-channel writer** for tickets; `ticketService` is the only ticket-state writer; `permissionService` is the only authorization decision point; `recoveryService` is the only automatic finisher of interrupted work. Each returns `{ ok, executed, code?, detail?, ... }` from `src/tickets/errors.js` — raw MongoDB and Discord errors never reach a caller.
- **One storage layer.** The ticket repositories are mounted inside the existing `createRepositories()` guard, so the collection allowlist, the single `connectionManager`, and `ensureIndexes()` are shared; no second connection manager or ODM was introduced.

### Collections and indexes

| Collection | Purpose | Key uniqueness |
| --- | --- | --- |
| `ticket_configs` | one guild ticket-system configuration document | unique `guildId` |
| `ticket_categories` | Nila-owned category configurations (`guildId` + `categoryId`) | unique `(guildId, categoryId)` |
| `tickets` | ticket records and their lifecycle state | unique `(guildId, ticketId)`, `(guildId, ticketKey)`, and partial uniques on `(guildId, channelId)`, `(guildId, requestKey)`, `(guildId, openSlotKey)` |
| `ticket_events` | append-only ticket history | indexed `(guildId, ticketId, createdAt)`, `(guildId, createdAt)` |
| `ticket_counters` | atomic per-guild ticket-number allocation | unique `guildId` |

Non-unique query indexes cover the access shapes the phase requires: `(guildId, ownerId, status)`, `(guildId, categoryId, status)`, `(guildId, assignedStaffId, status)`, `(guildId, status, createdAt)`, `(guildId, health, updatedAt)`, and `(guildId, enabled, displayOrder)` for categories. Documents store only validated fields — never Discord objects, interaction payloads, functions, or copied message content — and the validators reject credential-shaped keys (`token`, `secret`, `password`, `authorization`, `messagecontent`, `rawinteraction`) and MongoDB-hostile keys on every write.

### Ticket identifiers

`ticketId` is a 1-based per-guild integer allocated with an atomic `$inc` + upsert on `ticket_counters` (`findOneAndUpdate`, `returnDocument: after`), so allocation is safe under concurrency and survives restarts. `ticketKey` is that number rendered as `T00001` by `formatTicketKey()` (5-digit zero pad, growing past 99999 naturally). The key is stored, indexed uniquely, and written into the channel topic; the default channel name is `ticket-{number}-{slug}` (`appearance.channelNameFormat`, `showTicketIdInChannel`). Identity never depends on a name: the key plus the unique `(guildId, ticketId)` / `(guildId, ticketKey)` indexes are the authority, and a channel is only ever linked or deleted after its topic is verified to contain the key. Numbers are never reused.

### Guild configuration and categories

- `configService.getConfig` creates (via the repository's `ensure`) and returns the schema-validated **disabled** default for a guild that has never used tickets; T1 ships disabled everywhere.
- `saveConfig` merges a partial patch through `mergeTicketConfigPatch`, which rejects `enabled`, `guildId`, `revision`, and storage columns, then validates the whole merged document before a conditional write on the read `revision` (preferred) or legacy `updatedAt`. A stale writer gets `CONFIG_STALE`; two interfaces cannot clobber each other. Every ticket config, category, and panel document carries a monotonic integer `revision` (default 1, backfilled once for older documents, incremented atomically on every write, never settable through a patch), so concurrent edits are detected even when two writes land in the same millisecond — a case plain timestamp comparison cannot catch (see the T3 section).
- **Activation is separate.** Only `enable()` / `disable()` change `enabled`, both recheck the caller's live Discord `Manage Server` permission at the moment of the call, `enable()` additionally refuses when no enabled category exists (`NO_CATEGORIES`) or when the configured default category is missing/disabled (`DEFAULT_CATEGORY_DISABLED`), and the result is re-read from storage before it is reported. `setEnabled` records the acting administrator in `updatedBy`.
- Categories are Nila-owned records referencing Discord resources **by id only** (`discordParentCategoryId`, `staffRoleIds`, `additionalStaffUserIds`). They carry name/description/emoji, enabled flag, `displayOrder`, priority and per-user-limit overrides, `allowOwnerClose`, `requireClaim`, `closedAccess`, transcript flags, automation hints, up to 20 opening questions, and a welcome message. Patches cannot rewrite `guildId`, `categoryId`, or `createdAt`. Reordering requires the complete known set (`INCOMPLETE_ORDER` / `CATEGORY_NOT_FOUND`), duplication copies settings but never tickets, and deletion is refused while open tickets exist (`CATEGORY_IN_USE`) or while the category is the guild default (`CATEGORY_IS_DEFAULT`) — closed tickets and event history are always preserved. The per-guild bound is `LIMITS.MAX_CATEGORIES_PER_GUILD` (250), not a UI count.
- **Member-facing views are projected**: `publicCategoryView` and `listOpenableCategories` expose only what a member choosing a category needs, and never staff role/user ids or the parent category id.

### Creation flow

Pre-checks run in a fixed order before anything is written: guild scope → system enabled → actor authorized (human, in-guild) → `requestKey` idempotency lookup → category resolution → category enabled → title → priority → opening answers → guild active cap → bot permission check → parent category verification → per-user slot read. Only then does the flow allocate a number, insert the `pending_creation` record with its reserved open slot, create the private channel, link the record, apply the stored access policy, and best-effort send the category welcome message; a `ticket_created` event closes the operation.

- **Duplicates are prevented by storage, not by a check-then-insert.** The unique partial index on `(guildId, requestKey)` makes a retried request resolve to the existing ticket (`deduplicated: true`), and the unique partial index on `(guildId, openSlotKey)` — a slot is `<ownerId>:<index>` — makes the per-member open-ticket limit hold under concurrency, with at most `LIMITS.CREATION_SLOT_RETRIES` (5) bounded retries. Reading existing slots first is only an optimization.
- **Never a false success.** A missing bot permission is reported as `BOT_PERMISSION_MISSING` with the actual bit names before any record exists; a channel-creation or persistence failure rolls the pending record back; and if the rollback itself fails, the record is left flagged with `CHANNEL_ORPHANED`/`TICKET_ORPHAN_CHANNEL` plus a logged error rather than being reported as created. A channel whose ownership topic does not verify is never deleted. A repeated request carrying an already-used `requestKey` returns the existing ticket with `deduplicated: true` instead of creating a second one.
- Access is always private: `@everyone` is explicitly denied `ViewChannel` (and the read/write bits) in every mode, and only the bot, owner, assignee, configured staff roles/users, and participants are granted anything.

### Lifecycle and events

`status` moves only along `pending_creation → open → closed` (and `closed → open` on reopen); anything else is `INVALID_TRANSITION`. `syncState` (`none`, `channel_link_pending`, `close_permissions_pending`, `reopen_permissions_pending`, `channel_orphaned`) records which Discord-side effect still has to land, and `health` (`ok`, `needs_admin_repair` + `healthReason`) records what an administrator must look at.

Claims, releases, assignment, participant add/remove, rename, priority, category transfer, close, and reopen are each one conditional write (`compareAndUpdate` with the exact `status`/`syncState`/list the caller read) followed by the Discord effect and a finalize write — so two simultaneous claims produce exactly one winner and the loser gets `ALREADY_CLAIMED` or `CLAIM_CONFLICT`. When Discord refuses an effect the stored change is rolled back and the result reports `applied: false` / `rolledBack: true` with the Discord code; when the finalize write fails the marker stays set and the result says `needsRecovery: true` instead of claiming completion. History is append-only (`ticket_events`): claims, assignments, closes (`closedBy`, `closingReason`), reopens (`reopenedAt`, and the previous closer kept in event metadata) and transfers are never overwritten, and a rolled-back participant change is recorded as rolled back rather than as a grant. Closing restricts access and releases the owner's slot but **never deletes the channel**; reopening restores the stored policy and reacquires the slot. `assertPage` bounds listings and history; `listTickets` scopes `mine` to the caller and only allows `staff` scope for authorized staff. Ticket documents keep `channelId`, `ticketKey`, `openingAnswers`, `closedAt`/`closedBy`/`closingReason` and the category's transcript flags, which is the boundary a later transcript export reads — no transcript generation exists in T1.

### Permission model

`permissionService.authorize()` is called at the moment each operation runs; UI visibility is never a security check. It resolves the actor first (guild scope, snowflake, cross-guild member rejected, bots/webhooks and the bot's own member rejected) and then evaluates live: guild owner, `Administrator`/`Manage Server` holders, configured guild and category staff roles/users, and `Manage Messages` holders are staff; role status is recomputed from the member's current role cache on every call, so removing a role or clearing a staff list revokes access at the next operation with nothing cached. Owners reach only their own tickets; participants only tickets they were added to; a ticket whose `guildId` differs from the acting guild is reported as `TICKET_NOT_FOUND` rather than confirming existence. Owners may close only when the category allows it (`OWNER_CLOSE_DISABLED` otherwise). Denied reads are indistinguishable from nonexistent tickets (`nonConfirming` authorization on `getTicket` and `getHistory`), so no probe can tell whether another member has a ticket or what it says. Returned role objects carry booleans only (`publicRoles`), never raw role ids as a capability token.

Failure codes include `GUILD_ONLY`, `ACTOR_UNRESOLVED`, `ACTOR_NOT_HUMAN`, `CROSS_GUILD_MEMBER`, `UNKNOWN_ACTION`, `ADMIN_REQUIRED`, `STAFF_REQUIRED`, `TICKET_NOT_FOUND`, `NOT_PERMITTED`, `OWNER_CLOSE_DISABLED`, `TICKET_SYSTEM_DISABLED`, `NO_CATEGORY_CONFIGURED`, `CATEGORY_NOT_FOUND`, `CATEGORY_DISABLED`, `CONFIG_INVALID`, `CONFIG_STALE`, `CATEGORY_STALE`, `PANEL_STALE`, `STALE_CONFLICT`, `DRAFT_INVALID`, `DRAFT_DIRTY`, `CONFIG_NOT_FOUND`, `CATEGORY_EXISTS`, `CATEGORY_IN_USE`, `CATEGORY_IS_DEFAULT`, `CATEGORY_LIMIT_REACHED`, `INCOMPLETE_ORDER`, `INVALID_REQUEST`, `TITLE_INVALID`, `PRIORITY_INVALID`, `ANSWERS_INVALID`, `REASON_INVALID`, `USER_LIMIT_REACHED`, `GUILD_LIMIT_REACHED`, `NOT_CLAIMED`, `ALREADY_CLAIMED`, `CLAIM_CONFLICT`, `PARTICIPANT_CONFLICT`, `NOT_A_PARTICIPANT`, `TARGET_NOT_STAFF`, `TARGET_NOT_MEMBER`, `TARGET_UNRESOLVED`, `INVALID_TRANSITION`, `TICKET_CREATION_INCOMPLETE`, `TICKET_UNRECONCILED`, `BOT_PERMISSION_MISSING`, `BOT_PERMISSION_UNKNOWN`, `PARENT_CATEGORY_MISSING`, `PARENT_CATEGORY_INVALID`, `CHANNEL_NOT_FOUND`, `CHANNEL_MISSING`, `CHANNEL_LINK_FAILED`, `PARTIAL_APPLY_FAILED`, `OWNERSHIP_UNVERIFIED`, `OVERWRITE_LIMIT_REACHED`, `DISCORD_PERMISSION_REJECTED`, `DISCORD_API_ERROR`, `DATABASE_UNAVAILABLE`, `REPOSITORY_UNAVAILABLE`, `PERSISTENCE_FAILED`, `AUDIT_PERSISTENCE_FAILED`.

### Restart recovery

MongoDB and Discord cannot be updated atomically, so every interrupted operation is finished or flagged from its persisted marker after startup by `recoveryService`:

- pending creation with a recorded channel id → verify the topic and link, or flag `CHANNEL_MISSING` / `CHANNEL_IDENTITY_MISMATCH`;
- pending creation without one → after a 5-minute grace (`PENDING_CREATION_GRACE_MS`, so an in-flight creation is left alone) adopt a channel only when exactly one channel matches **both** the stored expected name and the ticket key in its topic; more than one match, or no match, is abandoned for administrator review rather than guessed at, and no duplicate channel is ever created;
- `close_permissions_pending` / `reopen_permissions_pending` → re-apply the stored policy and finalize the state (a finished close keeps `closedBy` null and records that Nila completed it);
- `channel_link_pending` on an existing channel → verify identity, re-apply the deterministic policy (which also drops stale overwrites for deleted roles), and clear the marker;
- `channel_orphaned` / `needs_admin_repair` → reported with identifiers and **never deleted**, because an orphaned channel may hold conversation an administrator has to inspect.

Recovery reads only the client's guild cache (no HTTP fetch of a possibly-deleted channel), only scans guilds whose `ticket_configs.enabled` is true, is bounded (`RECOVERY_GUILDS_MAX` / `RECOVERY_ITEMS_MAX`, 200 each), wraps every guild and every ticket individually, and re-applies access strictly from stored configuration — it never grants `@everyone` anything, never invents staff, never widens access, and its failures are logged or returned as codes so bot startup cannot crash. It runs once from the existing `clientReady` handler in `index.js` (`runTicketRecovery`, fire-and-forget, skipped with a logged warning while `connectionManager.getState()` is not `connected`); no second startup handler or listener was added.

### Discord API constraints respected

`channels.create` accepts at most 10 permission overwrites, so the deterministic policy is capped at `MAX_CHANNEL_OVERWRITES = 10` with a fixed grant priority (`@everyone` deny → bot → owner → assignee → staff roles → staff users → participants) and any excess reported as `OVERWRITE_LIMIT_REACHED` with `truncatedOverwrites` and the dropped identities — the limit is never silently exceeded and never raises an unhandled API error. Channel names stay within Discord's 100-character bound (slug built and truncated by `buildChannelName`). Audit-log reasons are truncated to 500 characters. Discord failures are mapped to stable codes (`10003` → `CHANNEL_NOT_FOUND`, `10008` → `MESSAGE_NOT_FOUND`, `50013` → `DISCORD_PERMISSION_REJECTED` with the missing bit names when Discord reports them, `30001`/`40001` → invalid-overwrite codes, everything else `DISCORD_API_ERROR`). Permission checks are least-privilege and pre-flight: `REQUIRED_BOT_PERMISSIONS` is exactly `ViewChannel`, `SendMessages`, `ManageChannels`, `ReadMessageHistory`, `AddReactions`, `AttachFiles`, `EmbedLinks` (the bot's own channel overwrite additionally grants itself `ManageChannels` and `ManageRoles` so later overwrite edits succeed), `Administrator` satisfies all of them, and if the bot's permissions cannot be read at all the operation fails closed with `BOT_PERMISSION_UNKNOWN` rather than guessing. Slash commands are still deployed only through `npm run deploy:commands` — starting the bot never deploys anything, and T1 adds no command.

### Limitations

- The per-user open-ticket limit is bounded by `LIMITS.MAX_OPEN_TICKETS_PER_USER` (50) and the guild cap by `MAX_TICKETS_PER_GUILD` (50); both are storage limits, and a guild that needs more must raise them deliberately.
- Ticket numbers are per guild; there is no global ticket id, cross-guild search, or shared staff view.
- Overwrite truncation means a ticket with more than the budget of distinct staff/participant identities cannot be fully granted in one channel; the excess is reported, and the recommended configuration is staff roles rather than long user lists.
- Recovery can only see what is in the guild cache at startup, so a channel created while Nila was offline is adopted only if its name and topic still match the record.
- Duplicate-delivery protection for creation depends on the caller supplying a stable `requestKey`; without it, only the per-user slot index prevents a second ticket.
- `requireClaim`, `autoCloseAfterHours`, `claimReminderMinutes`, `notifyLogChannel`, `logChannelId`, `panels`, and the transcript flags are validated and stored, but nothing acts on them yet — there is no scheduler, no log writer, and no panel builder in T1.

## Ticket Panels and Member UI (Phase T2)

### Panel model and management

- Panels are guild-scoped documents addressed by stable `panelId` (2–32 chars, unique per guild, independent of the display name): name, enabled, title, description, colour, thumbnail/image/author/footer assets, branding flag, layout (`buttons`/`dropdown`/`hybrid`), ordered category references (each with button label/emoji/style, menu label/description/emoji, and `button`/`menu`/`auto` placement), publication channel/message markers, and audit timestamps. Image URLs must be http(s); colours are `#RRGGBB`.
- `panelService` offers create, retrieve, list, update (patch merge; identity and publication markers are unpatchable), duplicate (new id, settings copied, publication reset to draft), enable/disable, safe delete (removes only the panel document — categories, tickets, events, and history survive), full validation, ordered-category resolution, ephemeral preview, publish, published-message update, and republish. Every management call requires live `Manage Server` rights; saving or previewing never publishes.
- Category references resolve only in the owning guild: missing references fail (`PANEL_UNKNOWN_CATEGORIES`), disabled categories are flagged (`disabledCategoryIds`) and rendered disabled rather than silently dropped, and a panel with no categories cannot be published (`PANEL_EMPTY`).

### Layouts and Discord limits

- `buttons`: one button per selected category (5 per row, 5 rows, 25 per message). `dropdown`: one string-select menu (25 options). `hybrid`: chosen categories as buttons, the rest in the menu. `validatePanelLayout` checks counts, label/description lengths, custom-ID lengths, and embed text caps before publication and returns counts plus the nearest valid alternative (`suggestedLayout`, `alternative`) instead of truncating.
- Large collections use `renderPanelPage`: dropdown pages of 25 options and button pages of 20 (one row reserved for Previous/Next navigation). The repository itself is never capped at 5/10 categories (`PANEL_ENTRIES_MAX` 250, matching the T1 category bound).
- Custom IDs are compact (`tp:<panel>:<category>`, `ts:<panel>:p<page>`, `tm:<panel>:<category>`, `t2x:<token>`, `tt:<ticketId>:<op>`, all ≤ 100 chars) and carry no guild, names, or authorization claims; every interaction reloads guild, panel, category, and config from storage and rejects stale, disabled, deleted, or cross-guild controls.

### Member flow, forms, welcome, and controls

- Buttons/selects route through `createTicketPanelHandler` (wired into `src/events/interactionCreate.js`): prompt acknowledgement, exactly-once replies, expired-token tolerance, and idempotent creation via `requestKey` `t2:<panel>:<category>:<user>` (repeats report the existing ticket with `deduplicated: true`). Creation always calls `ticketService.createTicket`; no handler creates channels directly.
- Categories with opening questions open a Discord modal (≤ 5 inputs, labels ≤ 45 chars, per-question min/max applied; answers revalidated server-side with `validateOpeningAnswers`). Forms longer than one modal continue through an opaque follow-up token (`t2x:<token>`, guild- and owner-scoped, 10-minute expiry, single-use); no ticket exists until the final step validates. Over-long question labels fail with `QUESTION_LABEL_TOO_LONG` rather than producing a malformed modal.
- After creation the handler posts one rich welcome embed (ticket key, category, status, owner mention, assigned staff when present; `@everyone`/`@here` neutralized; explicit `allowedMentions` for owner + staff only) plus the ticket controls (Claim, Close, Add participant, More actions → remove/rename/priority/transfer/release). A welcome-send failure is logged and reported with a retry path (`sendTicketWelcome` is safely repeatable) and never creates a second ticket. Controls render by role but every action re-runs the T1 service authorization; Close uses the existing confirmation flow and never deletes the channel.

### Commands and publication

- `/ticket-panel` (Manage Server default, guild-only): `create`, `list`, `preview` (ephemeral, never publishes), `publish` (validates panel, verifies the channel belongs to the guild, checks View/Send/Embed-Link permissions, sends, then persists markers — a send whose persistence fails returns `PUBLISH_STATE_NOT_SAVED` and never claims success), `update` (one setting: name/title/description/layout/colour/enabled/categories), `disable`, `delete` (confirmed; keeps categories, tickets, history). ### Drafts, revisions, and conflicts

- Each session clones the persisted config, categories, and panels plus their integer `revision` tokens into a draft; dirty state is stable-JSON comparison. Sessions belong to one guild and one initiating manager; every control re-resolves session, guild, owner, and Manage Server rights.
- Saving validates the whole draft (schemas, panel references, component limits, form constraints; missing roles/channels warn only), pre-flights fresh revisions, then commits config → updates → creates → guarded deletes through revision-conditional writes (`expectedRevision`, new `CATEGORY_STALE`/`PANEL_STALE` codes alongside `CONFIG_STALE`). The first conflict stops the commit with `STALE_CONFLICT`, persisted data preserved, and the draft kept for review. Undo reloads persisted settings and never touches tickets.
- The `revision` token is the fix for the reported same-millisecond `updatedAt` collision: it defaults to 1, is backfilled once for older documents, increments atomically (`$inc`) on every write including legacy timestamp-guarded writes, and can never be set through a patch (rejected as `CONFIG_INVALID`/`CATEGORY_INVALID`/`PANEL_INVALID`). The legacy `updatedAt` comparison path is kept for backward compatibility, and since Phase T4 its stored timestamp is clamped strictly past the previously stored value on every write, so same-millisecond stale writes are rejected deterministically instead of racing (see the T4 section).
- Since Phase 3F.6 the caller-provided revision contract also covers reminder/auto-close `saveSettings`, the category/panel/system enable toggles, and reminder/auto-close/survey activation: an integer `expectedRevision` is an atomic guarded write (`REMINDER_STALE`/`AUTOCLOSE_STALE`/`CATEGORY_STALE`/`PANEL_STALE`/`CONFIG_STALE` on mismatch, nothing written), a provided non-integer fails explicitly, and omitting it keeps the documented legacy path for callers without UI state. Guarded writes never backfill legacy revision-less documents. The `/tickets` dashboard and `/ticket-setup` wizard pass their snapshot revisions on these paths (including a fix for the wizard panel toggle, which called a nonexistent method); single-shot `/ticket` and `/ticket-panel` commands keep the legacy path.

## Ticket Transcripts and Audit History (Phase T5.1)

Implemented in `src/tickets/services/transcriptService.js` (wired into `createTicketSystem` as `transcriptService` and into `ticketService.closeTicket` as a post-close hook), `src/tickets/transcripts/` (`store.js`, `reader.js`, `renderer.js`), `src/tickets/validators/transcriptValidator.js`, the `ticket_transcripts` collection in `src/database/ticketRepositories.js` (4 new indexes: unique `(guildId, transcriptId)`, `(guildId, ticketId, createdAt)`, unique partial `(guildId, requestKey)`, and `expiresAt`; 46 indexes and 19 collections in total since T5.4), `src/commands/transcript.js`, and `test/ticketTranscriptsT5.test.js` (27 offline tests). T1–T4 services are reused, never rewritten: close/reopen/history semantics are unchanged, with one backward-compatible T1 extension — `closeTicket` results now carry a `transcript` field (`{ attempted: false }` unless automatic generation ran).

### Architecture

- **Generation** reads the ticket record, its `ticket_events` history (capped at `TRANSCRIPT_EVENTS_MAX` with an `EVENTS_CAPPED` gap), and the ticket channel's message history through a paginated newest-first reader (100 per page, at most `TRANSCRIPT_MESSAGES_MAX` messages). Anything that keeps the transcript from being whole (missing channel, failed pages, malformed attachments, caps) is recorded as a gap code and `complete: false` — never silently dropped.
- **Artifact format** is versioned JSON only (no HTML is ever generated): ticket header, opening answers (when the category includes them), chronological messages (author id/name, timestamp, content, attachment filename/URL — URLs are recorded, never fetched), lifecycle events, and a completeness block. Artifacts over `TRANSCRIPT_ARTIFACT_BYTES_MAX` shed oldest messages in documented 10% steps (`ARTIFACT_CAPPED`, `truncated: true`, dropped count), never silently.
- **Storage:** MongoDB holds only the metadata document (`ticket_transcripts`: guild/ticket/transcript ids, optional `requestKey`, status, format, counts, completeness, requester, delivery state, retention deadline, error codes). Artifact bytes live in a local directory store (`data/transcripts/`, overridable via `TRANSCRIPT_STORAGE_DIR`, files `0600`, traversal-proof generated references). No public URLs are invented and internal paths are never exposed; delivery sends file bytes to a private destination.
- **Delivery (private by default):** an explicit channel must be the ticket channel or the configured destination (anything else is `INVALID_DESTINATION`); otherwise the configured `destinationChannelId` is used (validated for existence, type, and bot send permissions); otherwise a DM to the requester; otherwise the transcript is stored with delivery `skipped`. Generation and delivery are reported separately — delivery failure never claims success and preserves retry state. `retryDelivery` resends without regenerating; already-delivered retries return `alreadyDelivered` with no resend and no new audit entries. Same-`requestKey` requests deduplicate to the generated record (failed attempts never block regeneration). An optional owner DM copy (`dmOwnerCopy`) is best-effort and never fails the request.
- **Closure integration:** `closeTicket` calls `generateForClosedTicket` once after a successful close. It runs only when the guild policy `transcript.autoGenerate` is explicitly `true` **and** the category's `transcript.enabled` is true (automatic generation stays disabled by default). Delivery prefers the configured destination, falls back to the closed ticket channel, else stores with delivery `skipped`. Any transcript failure annotates `result.transcript` and the event stream; the closed ticket is unaffected.
- **Retention:** `transcript.retentionDays` (null = keep indefinitely) sets `expiresAt`; `cleanupExpiredTranscripts` (via `/transcript cleanup`, Manage Server only) removes expired artifacts and metadata, tolerates missing files, and reports `{ checked, removed, failures }`.
- **Authorization:** every operation re-authorizes through the view-history policy (owners/participants/assignees/staff/managers, non-confirming), plus the guild `allowOwnerRequest` flag for non-staff requesters. No logs or error messages carry message content, attachments, tokens, or paths.
- **Configuration** (`tickets.transcript`: `autoGenerate`, `destinationChannelId`, `retentionDays`, `allowOwnerRequest`, `dmOwnerCopy`) validates as a complete block through `saveConfig`; saving it never generates, delivers, or activates anything. Documents written before T5.1 validate with safe defaults. The `/tickets` dashboard accepts the key for future UI use; no dashboard views were added.
- **Commands** (`/transcript`, guild-only, authorization server-side): `create ticket_id channel?`, `retry transcript_id`, `view ticket_id page?` (lifecycle events only, 10 per page, ephemeral), `cleanup`. Registration stays explicit via `npm run deploy:commands` (18 commands total); startup still never deploys.
- **Audit events** (append-only, metadata only): `transcript_requested`, `transcript_generated`, `transcript_delivered`, `transcript_delivery_failed`, `transcript_expired`. Retries and duplicates add no entries.

## Advanced Ticket Staff Management (Phase T5.2)

Implemented in `src/tickets/services/noteService.js` and `src/tickets/services/staffService.js` (both wired into `createTicketSystem`), `src/tickets/validators/noteValidator.js`, the `ticket_notes` collection in `src/database/ticketRepositories.js` (2 new indexes: unique `(guildId, ticketId, noteId)` plus `(guildId, ticketId, createdAt)`; 46 indexes and 19 collections in total since T5.4), `src/commands/ticket.js` (guild-only `/ticket` with twelve subcommands including `stats`), and `test/ticketStaffT5_2.test.js` (33 offline tests). Claim, release, assign, reassign, and category transfer reuse the T1 conditional-write operations unchanged (including the channel-control buttons from T2); T5.2 adds the read-side staff views, the notes domain, and the command surface — no lifecycle logic was duplicated.

### Assignment semantics

- **Claim** is self-service: a staff member takes an unclaimed open ticket (`assignedStaffId: null` → self) through one conditional write, so two simultaneous claims produce exactly one winner and the loser gets `ALREADY_CLAIMED`/`CLAIM_CONFLICT`. The actor and timestamp (`claimedAt`) are stored and the history is append-only.
- **Assignment** is supervisor action: a staff member assigns or reassigns a ticket through one conditional write on the currently-read assignee, so concurrent changes conflict instead of overwriting (`ASSIGN_CONFLICT`). The target must be a guild member independently eligible as staff (`TARGET_NOT_MEMBER`/`TARGET_NOT_STAFF`, cross-guild members rejected); the new assignee's channel access is applied and partial application is reported (`PARTIAL_APPLY_FAILED`) without widening `@everyone` or dropping existing grants.
- **Release** clears the assignment and is permitted to the claimant and to other staff (documented policy: any staff may return a ticket to the queue); the released-from id and the full assignment trail stay in the event stream. There is no assignment deletion — only transitions, all audited.
- **Assignment history** (`getAssignmentHistory`) replays the `ticket_claimed`/`ticket_released`/`ticket_assigned`/`ticket_reassigned` slice of the audit stream chronologically under ticket-visibility authorization.

### Queue filters

`queryStaffQueue` pages open tickets (default 10, max 25 per page) with stable sorts (`newest`, `oldest`, `recently-updated`, the last with a ticket-id tiebreaker for same-millisecond writes): `unclaimed`, `mine` (owner/participant/assignee merge for any authenticated actor; `total` stays honestly unknown with a `hasMore` flag), `all`, `high-priority` (high + urgent), `category` (validated, must exist), `assigned` (validated staff id), and `recent`. Staff-only except `mine`; invalid filters fail with `INVALID_FILTER`, never with guessed results. "Awaiting staff response" is deferred — it needs response-tracking data that does not exist, and it is not inferred. Items project metadata only (key, title, priority, category, owner/assignee ids, participant count, timestamps, channel id for `<#channel>` navigation) — no answers, notes, or message content. Totals come from `countDocuments` with the exact listing filter.

### Transfer recovery

Transfers reuse the T1 ten-step operation (authorization, state and destination validation, access recomputation, owner/participant preservation, permission apply, category update, audit event, structured result). Discord failures after the category update keep the new category, flag `needs_admin_repair`, and leave overwrites byte-identical (verified: partial transfers never widen access); an administrator recovers by re-running the transfer or fixing the channel, and recoveryService still reconciles unreconciled markers. Database failures before Discord work fail closed with nothing changed.

### Internal note privacy

Notes (`ticket_notes`: author, 1–2000 char body, timestamps, bounded edit history) are staff-only in creation, reads, and edits — ownership alone never grants access. Edits are limited to the author or a manager, preserve every prior version (max 10, then `NOTE_EDIT_LIMIT`), and append `note_edited` events carrying ids only. There is no delete endpoint. Note bodies never enter logs, events, or error messages; `getHistory` filters `note_added`/`note_edited` for non-staff viewers; the transcript generator drops note events before rendering. Member history, transcripts, and welcome messages provably exclude note content (asserted byte-level in tests).

### Workload metrics

`getWorkloadSummary` (staff-only, guild-scoped) returns counts from indexed `countDocuments` calls only — open total, unclaimed, high-priority, per-enabled-category buckets, per-assignee buckets (from one bounded open-ticket read), and reassignment/transfer event counts over an explicit window (default 7 days, max 90, validated). First-response and resolution metrics ship in Phase T5.6 (see `getResponseMetrics`) over the recorded activity; they are still absent from this workload summary by design.

### Commands

`/ticket` (guild-only, authorization server-side): `claim`, `release`, `assign`, `unassign` (release), `queue` (filter/category/staff/page), `transfer`, `note-add`, `note-list`, `note-edit`, `workload` (window_days), `history` (assignment trail), `stats` (report/days/granularity/staff/page). Replies are ephemeral metadata summaries; queue lines link channels; note bodies appear only in staff-only note views. Registration stays explicit via `npm run deploy:commands` (18 commands total); startup still never deploys. Channel controls from T2 (Claim/Close/participants/More-actions incl. transfer and release) are unchanged and already route through the same services.

## Ticket Statistics & Reporting (Phase T5.3)

Implemented in `src/tickets/services/statisticsService.js` (wired into `createTicketSystem` as `statisticsService`, reusing `staffService.getWorkloadSummary` for workload sections instead of reimplementing it), one additive `actorId` option on `ticketEvents.countByTypes`, one justified compound index `ticket_events_guild_type_created` (39 indexes total; the T1 index contract is untouched), the `stats` subcommand on the existing guild-only `/ticket` command (no new top-level command, no deployment-list change, startup still never deploys), and `test/ticketStatisticsT5_3.test.js` (22 offline tests).

### Implemented metrics and their data sources

- **Volume** (`getVolumeSummary`): created/closed/reopened count `ticket_created`/`ticket_closed`/`ticket_reopened` transition occurrences in `[since, until]` (inclusive, millisecond-exact), plus current open/closed snapshot counts from the ticket documents — so reopened tickets never double-count as closed.
- **Categories** (`getCategoryBreakdown`): per-category open/closed/total from indexed ticket counts over the full enabled set (bounded pagination), sorted by total with id tiebreaks. Current assignment only.
- **Staff activity** (`getStaffActivity`): per-member claims, assignments, reassignments, transfers, and closures from actor-stamped events in-window. Factual counts only — never rankings or productivity scores. Default roster is configured staff users plus current assignees (bounded); callers may pass up to 25 explicit ids.
- **Period series** (`getPeriodSeries`): day/week/month buckets (max 31) with per-bucket volume, used by trends.
- **Comparison** (`comparePeriods`): two equivalent non-overlapping windows sharing one boundary, with absolute and percentage deltas. Zero baselines yield explicit labels — `new (no baseline activity)` (percent null) or `steady` — never an infinite percentage.
- **Report** (`getReport`): composed volume/categories/staff/workload/trends sections with selectable subsets.
- **Workload**: reused from T5.2, not duplicated.

### Deferred metrics and why

Original-category historical totals (would need an unbounded per-ticket created-event join — transfers move the record, so only current assignment is reported); rankings or productivity interpretation of activity counts (refused on principle). Response and resolution times and awaiting-staff-response tracking were deferred here and are implemented in Phase T5.6 (`getResponseMetrics`, the derived `awaiting` queue filter) over the passively recorded activity — still never invented for tickets whose data predates the recording.

### Period and timezone semantics

All boundaries are UTC: days start 00:00Z, weeks Monday 00:00Z (ISO 8601), months the 1st 00:00Z. UTC has no daylight-saving transitions, which is why it is the reporting timezone. Windows are validated (valid Dates, start ≤ end, max 366 days) and every rendered report prints its ISO period with the UTC label.

### Repository and index changes

`countByTypes` gained an optional `actorId` filter (backward compatible); every statistics query is a guild-scoped `countDocuments` (documents are never loaded to compute totals; category configuration pages are the only bounded lists). One new index — `ticket_events { guildId: 1, type: 1, createdAt: 1 }` — serves every `{guild, type, time-window}` statistics query; no production migration is run by code.

### Commands

`/ticket stats` (guild-only, staff-only via the existing `VIEW_GUILD_TICKETS` check, ephemeral metadata-only replies): `report` (summary/volume/categories/staff/trends/workload/compare/surveys), `days` (1–90), `granularity` (daily/weekly/monthly), `staff` (single-member activity), `page` (stateless pagination for long category/staff/trend lists). Empty datasets render explicit zero/empty messages; replies stay within embed limits and carry no message content, notes, transcripts, answers, or survey comments. No collectors or sessions are created, so there is no interaction state to expire; repeated reads are idempotent.

Only the explicit `setSurveyEnabled` manager operation flips the switch, and only after revalidating the stored policy; concurrent saves conflict via the config revision (`CONFIG_STALE`).
- Category overrides (`eligible`, nullable `allowComments`/`expiryHours`) merge onto the stored block through the existing revision-guarded category update. Overrides narrow but never enable: issuance additionally requires the guild master switch.
- Effective policy: scale `minRating–maxRating` (1–5 default, at most 10 choices in rows of five), comments on/off with a 1000-character server-enforced cap, delivery `ticket-channel` (default) or `dm`, expiry in hours (1–720, default 72).

### Issuance and delivery

- `maybeIssueSurvey` runs in the close hook only for closed tickets when the guild switch is on and the category is eligible. One survey per ticket max: a pre-check plus the unique `(guildId, ticketId)` index make repeated hook executions idempotent at the database level. Every failure mode (unreadable config, failed insert, unresolvable DM recipient, missing channel, Discord rejection) degrades to `{ attempted, ok: false }` — closure always succeeds.
- Delivery is private only: the ticket channel or a DM to the owner. Attempts are counted and capped at 3; undelivered surveys stay pending for a bounded manual `retryDelivery` (manager-only, no-op once delivered). No background scheduler exists.

### Member interface and response integrity

- Rating buttons (`sv:<guildId>:<surveyId>:r<rating>`, guild embedded so DM interactions stay guild-scoped) open a comment modal when comments are enabled, else submit immediately. The modal submit (`svm:…`) carries the rating plus an optional comment in one atomic write — a comment can never create a second rating.
- Every submission revalidates recipient, pending status, expiry (marking the row expired with one event), and the current policy from storage; custom IDs are pointers only. The response insert wins the unique `(guildId, surveyId)` race and the survey row follows with a conditional pending→submitted transition; losers resolve to the winner (`deduplicated: true`), never duplicating.

### Privacy and access control

- Submit authorization is recipient-match, not role-based; staff inspection, statistics, config, and cancel/retry require staff or manager rights as documented per operation. Cross-guild reads and writes fail closed.

Aggregates report counts and averages only, with no respondent identities. Records persist with ticket history (no auto-delete); retention policy beyond that is deferred and documented here rather than invented.

## Ticket Automation Foundation (Phase T5.5.1)

Durable job storage, safe scheduling, and auditability for future ticket automation. No automatic ticket actions exist: there is no auto-close, reopen, reminder, or assignment behavior in this phase — later phases build on this foundation. Implemented in `src/tickets/automation/` (wired into `createTicketSystem` as `automation`), `src/database/ticketAutomationRepositories.js` (3 collections, 6 indexes; 52 indexes and 22 collections in total), and `test/ticketAutomationFoundationT5_5_1.test.js` (47 offline tests). No new slash command, no deployment-list change, startup still never deploys. T1–T5.4 services are reused, never rewritten.

### Job schema and status transitions

- Persisted jobs carry `guildId`, `jobId` (16 hex), `jobType` (strict allowlist: `automation.noop`, `automation.test`), `status`, minimal flat `payload`, `dueAt`, `createdAt`/`updatedAt`, `attempts`/`maxAttempts` (1–10, default 5), `nextAttemptAt`, `leaseOwner`/`leaseUntil`, `idempotencyKey`, sanitized `lastErrorCode`/`lastError`, and cancellation/completion metadata. Every write is validated; payloads reject nesting, message content, and credential-shaped keys.
- Legal transitions: `pending → claimed | cancelled`; `claimed → pending (retry) | completed | failed | cancelled`; terminal states (`completed`, `failed`, `cancelled`) have no outgoing edges, so finished jobs never execute again. Unknown job types are rejected at schedule time and fail safely at execution time.
- Idempotency: `idempotencyKey` is required to schedule; repeats return the stored row with `deduplicated: true`, enforced by a unique partial index (the database, not a check-then-insert, is the arbiter). Cancellation of pending/claimed jobs is a conditional write; terminal jobs cannot be rewritten.

### Scheduler, leases, and worker model

- Bounded due scans (`status: pending`, `dueAt <= now`, retry gate, deterministic `dueAt`/`jobId` tie-break, limit ≤ 25) plus bounded expired-lease scans. Claims are atomic conditional updates carrying a finite lease (default 30s, 1s–5min). Loading a job never executes it; execution revalidates state, lease ownership, and policy first.
- Supported models: (A) one worker in one process and (B) multiple workers sharing the same MongoDB — claims, completions, retries, cancels, and lease recoveries are all status-and-`leaseOwner`-fenced conditional writes, so exactly one worker wins every race and a stale worker (expired lease reclaimed by someone else) is rejected without overwriting newer state. (C) Independent bot instances without a shared database are NOT supported and would diverge.
- Shutdown stops polling immediately and accepts no new work; the in-flight handler (bounded by registry contract) runs to completion, and unexecuted jobs keep recoverable leases. The loop idles on empty queues (no busy loop) and never blocks Discord interaction handling; no Discord calls happen anywhere in this module.

### Retries, recovery, and guarantees

- Handler errors classify as retryable (`RetryableAutomationError`, unknown throws) or permanent (`PermanentAutomationError`, validation failures, unknown types, disabled guild). Retryable failures use bounded deterministic exponential backoff with jitter (base 1s, cap 5min); attempts never exceed `maxAttempts` (exhaustion fails permanently as `MAX_ATTEMPTS_EXCEEDED`). Errors persist sanitized (allowlisted code, ≤200 chars); payloads and secrets never reach storage or logs, and a throwing handler cannot crash the process.
- Crash/restart recovery: pending jobs survive restarts (same MongoDB); expired claimed leases return to pending with attempts preserved and are reclaimed on the next tick. Cancel-vs-claim, cancel-vs-execution, and completion races resolve to exactly one audited outcome.
- Guarantee: at-least-once execution with durable fenced state transitions and idempotency requirements — exactly-once is NOT claimed for arbitrary external side effects. Handlers needing stronger semantics must be idempotent; uncertain outcomes (e.g., a completion write lost to a race) are reported as races, never as success.

### Policy gate and auditability

- Guild automation policy defaults to disabled; `savePolicy` rejects `enabled` (saving never enables), and only the authorized `setEnabled`/`enable`/`disable` path (revision-guarded) flips the switch. The executor checks the policy after claiming but before running any handler: disabled guilds fail jobs as `AUTOMATION_DISABLED` without executing. Manual ticket operations never consult this switch.
- Audit events (`scheduled`, `claimed`, `started`, `retried`, `completed`, `failed`, `cancelled`, `lease_recovered`, `stale_worker_rejected`) live in `ticket_automation_events` — guild-scoped, bounded, identifier-only — plus sanitized logger lines. Internal scheduling facts never enter ticket transcripts, staff notes, or member history.

## Advanced Automation Engine

## Security and Extension Rules

- Keep `DISCORD_TOKEN` in the ignored root `.env`; never print or commit secrets.
- Preserve least-privilege intents. Startup requests `Guilds`, `GuildMessages`, and privileged `MessageContent` plus `GuildMembers` (the last two require the Developer Portal Message Content Intent and Server Members Intent toggles for text-based detection and anti-raid join monitoring).
- Check permissions and resource authorization in server-side callbacks for every sensitive interaction; do not trust UI state or custom IDs alone.
- Acknowledge each Discord interaction once; use edit/follow-up paths after acknowledgment and handle expired interactions.
- Keep presentation builders separate from business logic. Confirmation display alone must not perform an operation.
- Reuse the existing configuration, builders, response helpers, logger, and tracking utilities. Avoid duplicate listeners and dependencies.
- Add offline tests for behavior and failure paths. Keep traditional embed and Components V2 message formats distinct.
- Update this guide when architecture or implemented feature status changes.
